# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

How releasing works: collect notes under `## [Unreleased]` while developing. The [Release workflow](.github/workflows/release.yml) (Actions -> Release -> Run workflow) moves them under the new version heading, bumps `ProjectSettings/ProjectSettings.asset` `bundleVersion`, commits, and creates the GitHub release using that section as release notes.

Release notes for versions before 1.5.0 are available on the [GitHub releases page](https://github.com/Pascal-Jansen/Bayesian-Optimization-for-Unity/releases).

## [Unreleased]

### Changed
- **Python packages now live in a private virtual environment, so the first Play after updating installs them once more.** 1.8.0 ran `pip install --user`, which every virtual environment refuses (a **Manually Installed Python** pointing at a venv never worked), as do externally managed Pythons (PEP 668: Homebrew, Debian/Ubuntu system Pythons); the user site is also shared with every other project of that user, so another project's `pip install --user numpy==…` silently changed what the backends imported. Now a configured interpreter that is itself a venv/conda environment receives the packages; any other interpreter gets a private environment at `<persistentDataPath>/BOData/python-venv` (a sibling `python-venv-<hash>` for each further base interpreter, so switching interpreters never wipes a working environment; on Windows a short folder under `%LOCALAPPDATA%\BOforUnity\` when that path would be too long), and the backends run with its Python. Only if no venv can be created (Debian/Ubuntu without `python3.13-venv`) does the launcher fall back to `--user`, and it says why. **The first Play after updating takes a few minutes (it downloads several hundred MB). Optional packages — openbo for MetaTAF, `open_clip_torch`/`pillow` for image embeddings — must be installed again with the interpreter the Console logs at startup as `Optimizer Python: …` (`"<that path>" -m pip install …`)**; the backends' "not installed" messages now print that interpreter.
- **The install scripts no longer install the Python packages** — Unity does, on the first Play. `Windows/installation_python.bat` installs Python 3.13 and the VC++ runtime, `MacOs/install_python.sh` the bundled Python 3.13, `Linux/install_python.sh` Python 3.13 with its `venv` module (deadsnakes PPA on Ubuntu releases without it, Debian 13+ from its own packages, instructions elsewhere); each checks that the interpreter can create virtual environments. `--venv DIR` additionally creates an environment with `requirements.txt` in `DIR` for **Manually Installed Python**.
- **Pinned versions are verified on every start** instead of trusting a stamp from the last install: a metadata probe (no torch import, about a second) compares every `==` pin in `requirements.txt` with what the backend's interpreter would import and reinstalls on a mismatch. The installed versions are written at the top of `output.txt`.
- **Interpreter discovery is capped at the tested Python minor version (3.13)** and prefers the bundled 3.13, as README 8.5 already stated; it used to take the newest 3.x, so a machine with Python 3.14 ran an untested stack. Newer minors are tried only after every 3.13 interpreter failed; if pip fails for one interpreter the next is tried (an unreachable package index stops at once); the same interpreter reached through several links is tried once; on macOS `/usr/bin/python3` (Apple's stub, which opens a Command Line Tools install dialog) is skipped. Discovery and all probes run off the main thread with timeouts, so a hanging interpreter cannot freeze the Editor.
- Linux installs take PyTorch from its CPU wheel index (`https://download.pytorch.org/whl/cpu`; `2.14.1+cpu` satisfies the `torch==2.14.1` pin) instead of PyPI's CUDA build with several GB of `nvidia-*` packages. Offline labs: wheels in `StreamingAssets/BOData/Installation/wheels/` are tried first on their own (`--no-index --find-links`), then together with the package index.
- Player builds keep only their own platform's Python installer: a build post-processor removes the other platforms' `StreamingAssets/BOData/Installation/<OS>` folders from the built player (macOS pkg 71 MB, Windows Python 28 MB + VC++ runtime 25 MB) and renews the ad-hoc signature of a macOS `.app` afterwards (an app signed with an identity is left untouched). The project's own Assets are never modified.
- **MC Samples defaults to 128 instead of 512** (inspector default, `BoForUnityManager` prefab, the four example scenes, and the fallback of `bo.py`, `mobo.py` and MetaTAF when the init message carries no value). Measured on the MOBO acquisition search (d = 4, 30–40 observations, fitted model fixed): 2–5 objectives 2.6–4.2× faster (e.g. 3 objectives 15.2 s → 5.0 s); the proposed design moved by 1e-3 to 1.7e-2 in the unit cube. Scenes created earlier keep their serialized value. DBO and CABOP do not use it. **The acquisition estimate changes with the value: do not upgrade within a running study, or keep 512 in its scene.**
- **MOBO and MetaTAF use the hypervolume reference point −1.1 in every objective (was −1).** With exactly −1, a Pareto-optimal design rated worst on one objective (common with extreme Likert ratings) added no hypervolume: for the designs (best, worst) and (worst, best) both rows were `IsPareto = TRUE`, yet coverage and `HypervolumePerEvaluation.csv` stayed 0 (now 0.21, then 0.41), qLogNEHVI saw no improvement from such designs, and a population model whose front consisted of such designs was refused by `meta_train.py` and skipped by MetaTAF. The value (`bo_normalize.HYPERVOLUME_REFERENCE_VALUE`) is used by qLogNEHVI, openbo's population terms, the coverage metric, the logged `ReferencePoint` (`[-1.1,-1.1]`) and `meta_train.py`'s front check. **Suggestions after the sampling phase and logged hypervolumes differ from earlier versions (hypervolumes are larger and not comparable across the change): do not upgrade within a running study.**
- **Contextual optimization with Manual or Image embeddings: context similarity now comes from the provided embeddings. Study-behaviour change: do not upgrade within a running study.** BoTorch's LCEMGP always learns a 1-d embedding per context and concatenated the provided one to it. A context without observations — README 8.13's main case, a new participant warm-started from earlier ones — never moves its learned value away from the random initialization, so how much the model transferred to the new participant depended on the torch seed (the fitted correlation between two contexts with the same manual embedding, the new one without data, ranged from 0.00 to 1.00 over seeds 0–5). The task kernel now sees only the provided embeddings (LCEMGP's RBF kernel and lengthscale range) plus one learned weight `w` that starts at 0: context correlation = (1 − w)·RBF(embeddings) + w·[same context], so contexts with identical embeddings are pooled until their data disagree. Results no longer depend on the seed. `Learned` embeddings: posteriors of observed contexts are unchanged.
- **`Normalize Embeddings` (inspector label formerly "L2-Normalize Embeddings"; field `normalizeContextEmbeddings`) standardizes Manual embeddings per feature instead of L2-normalizing each context. Study-behaviour change: do not upgrade within a running study.** L2 normalization keeps only a vector's direction: every positive 1-d embedding became 1.0 (ages 25, 40, 60 → three identical contexts) and proportional profiles merged ([3, 4] ≡ [6, 8]), so the model pooled the data of contexts that were meant to differ. Each Manual feature is now z-scored across the configured contexts (constant features, and every feature when there is only one context, become 0) and scaled so the contexts' mean squared distance from their centroid is 1. Image (CLIP) embeddings keep L2 normalization. The backend warns when contexts have identical embeddings or become identical through normalization. With only two or three contexts, see the caveat in README 8.13.1. Together with the previous entry and the unobserved-context fix below, on 40 simulated studies (2–4 contexts, positive 1–3-d feature profiles that determine the optimum, a current context with 0–3 observations) the current context's posterior RMSE fell from 0.454 (1.8.0) to 0.380; for a new participant without own data (30 studies) from 0.494 to 0.387 (Manual) and from 0.511 to 0.467 (Learned).
- `BestObjectivePerEvaluation.csv` and its mirror `HypervolumePerEvaluation.csv` written by BoTorch (`bo.py`) and DBO gain `Scale` (frame and direction of `BestObjective`) and `BestObjectiveRaw` (the same best observation in the objective's own units; empty on a contextual warm-start baseline row without current-context observations). `BestObjective` stays the normalized [−1, 1] maximize-space value that `coverage` reports — sign-flipped for a minimized objective, unlike every other log column. The columns are appended, so scripts reading by name or position keep working.
- **CABOP: the reuse tolerance and the cost model now work in fractions of each parameter's range. Study-behaviour change: do not upgrade within a running study.** `CABOP Tolerance` was compared with raw differences in parameter units, and the soft-cost kernel that drives cost-aware acquisition had a fixed bandwidth of 0.05 parameter units, so a parameter's units decided whether two designs counted as the same prototype. With the default tolerance 0.05, a parameter on [0, 0.1] treated every proposal within half its range as the design already built (2 distinct designs shown in 15 iterations), a parameter on [0, 100] was charged the full "acquired" cost for a 1 % move, and on [0, 0.01] every candidate cost about the same, so cost-awareness did nothing. Both are now fractions of the range (default 0.05 = 5 % of Upper − Lower); a run on [0, 0.1] or [0, 100] proposes the same designs, in relative terms, as on [0, 1], and **parameters on [0, 1] behave exactly as before**. Convert a tolerance given in parameter units by dividing it by the range (e.g. 2 on [18, 64] → 0.0435); tolerances outside [0, 1] are refused by the inspector check and the backend, the inspector field is a 0–1 slider, and Unity no longer silently turns a negative tolerance into 0. The backend prints each tolerance in parameter units at startup. The Fitts-law scene's and `FittsLawTask`'s CABOP tolerances were converted (2/46, 2/80, 5/296 of the pixel ranges).
- **CABOP warm start logs like BoTorch and DBO.** With *k* warm-start rows, CABOP numbered its evaluations from 1 again, so its logs did not continue the warm-start rows' numbering (README 8.12); it wrote no baseline metric row and set `IsBest`/`IsPareto` among the live rows only. Evaluations are now numbered *k* + 1, *k* + 2, … in every log and in the `parameters` messages, the compatibility metric file starts with a baseline row at Iteration *k*, and warm-start rows compete for `IsBest`/`IsPareto` as in `bo.py`/`mobo.py` (a live row better than none of them is not marked). `CABOPMetricsPerEvaluation.csv` keeps one row per evaluation of the run. The model takes over at the first evaluation whatever sampling count the init message carries (Unity already sends 0 under warm start, so its suggestions are unchanged). **The final-design candidates of warm-started CABOP runs change: do not upgrade within a running study.**
- **DBO suggestions are 1.3–1.7× faster with bit-identical suggestions**: the vendored dbo-torch scored its 1024 raw acquisition samples 10 at a time (`batch_limit` = restarts), now 128 at a time (`init_batch_limit`, as `bo.py`/`mobo.py` since 1.8.0). Measured on the pinned stack, one thread: d = 2, 0.42 s → 0.25 s per suggestion; d = 4, 0.70 s → 0.54 s; suggestions and fitted alpha identical to the last bit. The local patch is recorded in `dbo_torch/PROVENANCE.md`.
- The five Python backends share one protocol module, `bo_protocol.py` (socket listener, NDJSON reader, objectives wait, init parsing and validation, run-folder naming, log writers), and `bo.py`/`mobo.py` share their warm-start loader, model construction and observation-log append (`botorch_common.py`). The copies had drifted (three versions of the reader, two of the objectives wait); a protocol or robustness fix now reaches every backend. Apart from the fixes below, the backends send the same messages and write the same logs as before.
- Every `parameters` message carries `iteration`: the `Iteration` the design will be logged under in `ObservationsPerEvaluation.csv` (warm-start and sampling rows included). Unity keeps it as `BoForUnityManager.LastSuggestionLogIteration`.
- **Init messages up to 64 MiB** (was 1 MiB; environment variable `BO_MAX_RECV_BUF_BYTES`, which the error now names). Manual context embeddings take about 16 KB per context at 1280 dimensions and 51 KB at 4096, so a few dozen contexts ended the study at startup with "possible framing error or oversized message". Unity now refuses to send a larger init and says so. Large messages are also received in linear time (the reader re-scanned its whole buffer after every read).
- New Unity → Python message `{"type": "stop", "reason": "..."}`: the backend prints `Stop requested by Unity: <reason>` and exits with code 0, with every completed evaluation logged. Unity sends it for a perfect-rating stop (reason `perfect_rating`) and in place of the init message when it refuses an invalid configuration (`invalid_configuration`); before, it could only kill the process, so the reason never reached `output.txt` and the exit looked like a crash.
- **An existing user log folder from another condition is now reused.** Unity reserved its folder with "suffix if `LogData/<UserID>` exists at all", so a participant's second condition ran as `P01_1` — a different `userId` sent to Python and written into every log row — contradicting README 6.2.1. Now `P01` running condition B after A logs to `P01/B`; only a repeated `P01/A` gets `P01_1`. **Study-behaviour change: multi-condition participants keep one User ID across conditions — do not upgrade within a running study.**
- **A perfect-rating stop now runs the final-design round** (when **Enable Final Design Round** is on) instead of going straight to the end screen, and tells the backend to stop instead of killing it while it waited for objectives; Unity gives it up to 1 s to exit by itself. **Study-behaviour change for studies that combine Perfect Rating with the final-design round: participants who stop early now get the final round too — do not upgrade within a running study.**
- The perfect-rating check judges the value Python received — the mean of the objective's finite sub-measures within its window — instead of the average of all collected values: one unanswered item (NaN) made a perfect rating "imperfect" although Python got a perfect mean.
- **Automatic advance counts real time** (`WaitForSecondsRealtime`): a scene that paused with `Time.timeScale = 0` never advanced.
- New optional **Progress Text** (`progressText`, TMP_Text) shows `Iteration x / N` (or `Final design`) whenever a design is ready. New script API: `BoForUnityManager.Instance` (the running, persistent manager), `LastSuggestionLogIteration`, `FinalDesignLogIteration` (the `Iteration` of the final-design row, −1 until it is selected) and `TerminateWithError(text)`.
- `Optimizer` finds the manager on first use (`BoForUnityManager.Instance`, else its own GameObject's): every call silently did nothing until `Optimizer.Start` ran, so calls from another script's `Awake`/`Start` were lost. `GetParameterValue`/`GetParameter`/`GetObjective` warn once per unknown key — a typo returned 0 (or a detached `ParameterArgs`) all study long without a message — and `AddObjectiveValue` warns once per name that matches no objective.
- Final-design selection searches the shared log root first (the condition's folder or its `CABOP/<mode>` folder; the StreamingAssets, persistentDataPath and legacy roots as fallbacks), and the Console names the candidate pool (`IsPareto`/`IsBest`/`computed`/`all`) and the `Iteration` the row will be logged under, with a warning when no backend flag was available. Tie-break 2 ("least aggressive") now normalizes parameters by their configured bounds and measures the distance to the middle of the design space; it normalized by the spread observed in the log, so a dimension the optimizer had barely varied (e.g. 0.50–0.52 of [0, 1]) dominated the tie-break. Only ties on the first two criteria are affected.
- **Fitts law task: selections are registered on pointer-down (ISO 9241-9)** instead of on release. A release-based click only counted when press and release landed on the same target and added the release delay to every movement time. New inspector option `Selection Event` (`Pointer Down` default, `Pointer Click` = previous behaviour). **Movement times are shorter than with earlier versions: do not upgrade within a running study, or set `Selection Event = Pointer Click`.**
- Fitts law task: odd target counts use the ISO 9241-9 order (step (n + 1) / 2), so every movement has the amplitude D · cos(90° / n); the previous pairing alternated between two amplitudes (0.993 · D and 0.935 · D for n = 13). Even counts (the provided scene uses 12) keep their order. **Changes the target order for odd counts: do not upgrade within a running study.**
- Fitts law logs report ISO 9241-9 metrics per round: `FittsLawAppLog.csv` gains `SelectionEvent`, `IsoTrialCount`, `IsoWidthPixels` (W), `IsoAmplitudePixels` (D), `IsoID`, `IsoEffectiveAmplitudePixels` (De), `IsoEffectiveWidthPixels` (We = 4.133 · SD of the endpoint deviations along the task axis), `IsoIDe`, `IsoMovementTimeMs` and `IsoThroughputBitsPerSecond` (TP = IDe / MT), excluding each round's first trial; `FittsLawTrialLog.csv` gains `FromTargetX/Y`, `AmplitudePixels`, `EndpointDeviationPixels`, `EffectiveAmplitudePixels` and `IncludedInIsoMetrics`. Both files also gain `AppliedButtonSizePixels`/`AppliedButtonDistancePixels` (and the app log `AppliedLayoutAdjusted`; see Fixed). The objectives sent to the optimizer are unchanged.
- Fitts law logs use the `Iteration` of the same evaluation in `ObservationsPerEvaluation.csv` (`LastSuggestionLogIteration`; the final-design round uses `FinalDesignLogIteration`): under warm start they were numbered 1, 2, … while Python numbered the evaluations *k* + 1, *k* + 2, …, so a join on `Iteration` paired telemetry with the wrong designs. Values are written with round-trip precision instead of 3 decimals, and the `*Objective` columns hold exactly the value sent to Python (finite mean, clamped to the bounds; one unanswered item used to blank the column). When an existing log has the old columns, new rows go to `FittsLawAppLog_1.csv` etc. instead of being appended under a mismatching header.
- `Restart With Key` on `FittsLawTask` defaults to off (also in the scene) and only restarts a running round (see Fixed).
- QuestionnaireToolkit `started`/`finished` timestamps are ISO 8601 UTC (`2026-10-09T14:03:04.123Z`) instead of the machine's culture format (`10/9/2026 2:03:04 PM`, `09.10.2026 14:03:04`). **Column format change.**
- Demo scripts read their parameters by key (`Color-Red`…, `TargetSize`/`TargetEccentricity`, `<Cube|Cylinder>ColorR`…; positional fallback when a key is missing); `ColorGuesser` and `ObjectVariableExposer` normalize with the parameter's bounds, while `TargetClickerEvaluator` keeps reading the value itself as a fraction (its bounds narrow the size/eccentricity range, as before) and writes click times to the objective `AverageClickTimeMS` (fallback: the second objective). `ObjectVariableExposer` now fills its `colorR/G/B/A` and `isActive` fields, which were never assigned. The Examples scripts compile into their own auto-referenced assembly (`BOforUnity.Examples`), so scenes and user scripts keep working.
- **`MetaWeightsPerEvaluation.csv` joins on `Iteration` like every other log.** Its `Iteration` was the optimization step (1..N), so a join paired each weights row with the evaluation `numSamplingIterations` rows earlier — mostly a sampling-phase design the weights never influenced. `Iteration` is now the global evaluation index, and a new second column, `OptimizationStep`, keeps the step. Scripts reading columns by position must skip the new column; for files written earlier, add `numSamplingIterations` to `Iteration` before joining.
- **`MetaRunState.json` follows the run** (`schema_version` 2): like `DboRunState.json` it is rewritten atomically after every evaluation with `progress` (evaluations completed, last `Iteration`, latest hypervolume and source weights) and ends with `finished` plus `finish_reason` (`completed`, `stop_requested` with Unity's reason, `error`, `startup_abort`). A file still saying `"finished": false` belongs to a killed backend. It also records the hypervolume reference point, sources with identical trajectories and the population manifest. A locked file never ends the study.
- **`meta_train.py` names each population model after its run's path** (`<participant>_<condition>_<run>`, e.g. `p01_main_run`) instead of its position on the command line (`00_p01_main_run`). Rebuilding a population into the same `--out` with one more, or reordered, runs published renamed copies next to the existing ones (3 participants → 5 sources), so those participants were weighted twice in every later run. A run already in `--out` keeps the name it has there (also a 1.8.0 index-prefixed name, and also when it was built from another path: on another machine or before the project folder moved), two runs with the same path tail get a short path hash, existing artifacts are kept (`[KEEP]`) unless `--force` is given, and `--dry-run` checks the frame, runs and names without fitting, writing or needing torch/openbo. Explicit names: `--name` (once per run, also next to its run path) or `--names a,b,c`.
- **Population manifest `population.json`**: `meta_train.py` writes it into `--out` after every build (or alone with `--manifest-only`): name and SHA-256 of both files of every source and the frame digest. While it is present, MetaTAF aborts before the first trial if the population it loads differs in any way (a source added, removed, replaced or no longer loadable) and lists the differences. This enforces the guide's "freeze the population" rule, which was documentation only: a source folder that changed during a study (a sync client, a colleague adding a participant) silently gave later participants another treatment. Without a manifest nothing changes.
- The launcher checks the configuration (the shared `BoConfigValidator`, see Fixed) before the dependency setup, so a configuration error is reported at once instead of after a multi-minute install, and Python is never started for it.

### Fixed
- **A backend failure left the participant on a blank screen.** When Python rejected the init message, sent an invalid message or died mid-study, Unity wrote the error into `Output Text` but never showed the `Optimizer State Panel` containing it, never ended the loop and never cancelled a pending automatic advance. All failures now go through `BoForUnityManager.TerminateWithError`, which shows the panel with the message, hides loading and Next, ends the loop and stops Python; a failure to send the objectives does the same (a second questionnaire used to try again). The screen shows the backend's own last error line (e.g. `OSError: Port 56001 is already in use …`) with the path of `output.txt` instead of "The system could not be started…", and configuration errors found while building the init message are shown verbatim.
- **Configuration errors that crashed the backend after startup — often after the participant had finished the sampling phase — are caught before the study starts**: empty, duplicate or shared parameter/objective keys, keys equal to a fixed log column (`UserID`, `ConditionID`, `GroupID`, `Timestamp`, `Iteration`, `Phase`, `IsBest`, `IsPareto`, and `Context` with contextual optimization; case-insensitive), a parameter Lower Bound not below its Upper Bound, an objective Lower Bound above its Upper Bound, Raw Samples below Optimizer Restarts, a negative Seed with MetaTAF, and with CABOP a tolerance outside [0, 1] or prefabricated values outside the bounds. The inspector lists them in red under the objective list; the launcher and the manager refuse to start with the list on screen. The backends repeat the checks: **`Raw Samples` < `Num Restarts`** crashed BoTorch, MOBO, DBO and MetaTAF after the sampling phase ("n (10) cannot be larger than the number of provided samples (5)"), and **a parameter with Lower Bound = Upper Bound is now refused by all five backends** (BoTorch, MOBO and MetaTAF ran with a dimension that could never vary; DBO and CABOP already refused it). **Study-behaviour change: a study with such a parameter no longer starts — do not upgrade within a running study;** remove a fixed parameter from the optimizer and set it in the scene instead.
- **A log open in Excel ended the participant's session (Windows).** The backends rewrite `ObservationsPerEvaluation.csv` after every evaluation; while a researcher had it open, the write raised `PermissionError` and the backend died mid-study. Writes are now retried for 2 s; a log that stays locked is reported once (`Warning: could not write <file> …`), kept in memory and written as soon as the file is free again, and the study goes on. No row is lost — also not in the logs that are read back and rewritten for `IsBest`/`IsPareto`. While a log is locked, its complete content is also kept next to it as `<name>.unsaved.csv` (deleted after the catch-up), which survives a session that Unity ends by terminating the backend. Appended logs (metrics, execution times, DBO diagnostics, MetaTAF weights) behave the same. Unity's final-design row is retried for about a second and otherwise written to `ObservationsPerEvaluation_finaldesign_<timestamp>.csv` with an error naming the file, and the final-design selection reads logs that another program holds open (it skipped them and fell back to "no final design").
- **A crash during a log rewrite could truncate the study log.** Rewrites now go through a temporary file in the same folder, `fsync` and an atomic replace, so the log is always the previous or the new version. Where Windows refuses only the replace (a viewer that holds the file open without allowing deletion), the log is written in place as before. Logs keep their usual file permissions.
- **A malformed line while waiting for objectives hung both sides for an hour.** The reader skipped it; if it was the objectives reply, Unity was already waiting for the next design, so both sides waited for the 3600 s socket timeout. The backend now stops at once and shows the line (malformed lines at other times are still skipped with a warning). An `objectives` message without a `values` dict was reported by BoTorch, MOBO, DBO and MetaTAF as "No objectives received from Unity", as if Unity had disconnected; every backend now reports the malformed message.
- **A host project's global Json.NET settings broke the protocol.** Every `JsonConvert` call picked up `JsonConvert.DefaultSettings`: a camelCase resolver lowercased the keys Unity sent (`Trust` → `trust`, a missing-key error in Python), `MissingMemberHandling.Error` made every incoming message throw, `Formatting.Indented` split messages across lines (breaking NDJSON framing), and `PreserveReferencesHandling`/`DefaultValueHandling.Ignore` added `$id` keys or dropped `0`/`false` settings. Unity now uses private serializer settings with explicit values in both directions (and for the launcher's installed-package list).
- A multi-byte UTF-8 character split across two socket reads was also corrupted on the Unity side (`Größe` → `Gr��ße`, then a missing-key error that ended the session); received bytes are now decoded incrementally (1.8.0 fixed the Python side).
- **Stopping play mode or quitting mid-study reported a crash**: Python was killed before SocketNetwork learned the stop was intended, so "Socket closed by Python unexpectedly" was logged and a connection-failure handler queued. With domain reload disabled (Enter Play Mode Options), that handler and the manager singleton survived into the next play session; both are now reset at startup. A study stopped before the socket connected left the Python process running until its accept timeout, holding port 56001; it is now stopped.
- The backend's normal exit after `optimization_finished` (or after Unity's stop for a perfect rating) is no longer treated as a failure: when it was noticed while a round was running — typically the final-design round — 1.8.0 replaced the status text with "The system could not be started...". A non-zero exit at that point is logged as an error without interrupting the final round, and Unity gives Python up to 1 s after a stop or `optimization_finished` to save locked logs and exit before terminating it, so the final-design selection reads the finished logs.
- **A perfect-rating stop during the sampling phase left wrong `IsBest`/`IsPareto` flags** (`Perfect Rating In Initial Rounds`): the backends write provisional flags while sampling and correct them after the last sampling design, which the stop skipped. BoTorch kept its best-so-far flags (ratings 2, 5, 8 logged `IsBest` TRUE, TRUE, TRUE), MOBO and MetaTAF `IsPareto = FALSE` on every row (MetaTAF also after an error), so FinalDesignSelector chose among the wrong designs. The flags are now finalized before the backend exits.
- **Reload Scene On Advance works for scenes outside the Build Profiles scene list.** The scene was reloaded by name, which in the Editor fails for a scene missing from the list (the example scenes are not in the project's empty list), leaving the loading screen up after the first evaluation; by name, Unity could also load another folder's scene of the same name. It is now reloaded by build index, or by its asset path when it has none (Editor; AssetBundle scenes in players). An unsaved scene stops the study before it starts, with the fix on screen.
- **Duplicate managers in reloaded scenes could capture other scripts.** With **Reload Scene On Advance** each reload instantiates the scene's manager again, and it was destroyed only at the end of the frame, so `FindObjectOfType<BoForUnityManager>()` in other scripts' `Awake`/`Start` could bind to the doomed copy. The copy is now deactivated before it is destroyed, and a warning names what differs when it was configured differently (keys, backend or IDs) — e.g. a second condition scene that silently kept the first, finished manager running.
- **Questionnaire and optimizer could log one participant to different user folders.** A questionnaire that initialized before the manager's `Start` read the raw User ID, and the questionnaire's log root kept a trailing separator (`…/LogData/`) while the optimizer's had none, so their folder reservations never matched; when the folder existed, each chose its own suffix (`P01_1` vs `P01_2`). The questionnaire bridge's `UserId` now resolves the folder on first use, and roots are normalized.
- **Installed players with a read-only StreamingAssets folder could not run a study**: the launcher created the log root outside the `try` around the process start, so the coroutine threw, Python never started and `Update` threw every frame. All logs (optimizer, questionnaires, Fitts telemetry, final-design row) now share one root that falls back to `<persistentDataPath>/BOData/LogData` where StreamingAssets is not writable, and every launcher failure ends the session with the error on screen. Custom questionnaire result paths are unchanged.
- Objectives silently dropped sub-measures beyond **Number Of Sub Measures** (the last N were kept: 4 questionnaire items matching an objective with N = 3 discarded the first answer); a warning now says how many were ignored, and the submitted values are no longer trimmed in place.

## [1.8.0] - 2026-10-09

### Changed
- **The initial design is now a real Sobol design in every backend.** `draw_sobol_samples(n=1, q=N)` drew *one* point of an N·d-dimensional Sobol sequence and reshaped it — no better spread than independent uniform draws (mean centered L2 discrepancy, d=2, N=6, 200 seeds: 0.064 vs 0.061 for i.i.d. uniform and 0.019 for a real Sobol design). BoTorch, MOBO, DBO and MetaTAF now draw N points of one d-dimensional sequence with the same call (`n=N, q=1`), so all of them share the initial design for a given seed — MetaTAF previously used a different generator, so its participants started from other designs than the BoTorch control condition. CABOP's own Sobol draw is fixed separately (below). **Initial designs differ from earlier versions: do not upgrade within a running study.**
- CSV logs keep 10 significant digits instead of 3 decimals. Small ranges were erased (0.000274 on [0, 0.004] logged as 0.0; two objective values 0.0035 and 0.0041 both as 0.004), so the logs could not reproduce the evaluated design, and FinalDesignSelector, warm starts and Meta-TAF sources worked from different values than the participant experienced. 10 digits keep every bit of the float32 values Unity exchanges while hiding float64 round-trip noise (`6.0`, not `5.999999999999999`).
- **BoTorch/MOBO suggestions are 2.5–3× faster with identical candidates**: the 1024 raw samples are scored 128 at a time (`init_batch_limit`) instead of 5 at a time (measured: single objective 1.72 s → 0.57 s, two objectives 11.0 s → 4.4 s per suggestion).
- **The single-objective backends (`bo.py`, DBO) run PyTorch on one thread**: 1.4–1.6× faster per suggestion with identical suggestions at study sizes (measured d = 2–8, n = 12–80; e.g. DBO d=2: 2.26 s → 1.40 s, `bo.py` d=8, n=80: 0.79 s → 0.55 s), and the other cores stay free for Unity. The environment variable `BO_TORCH_THREADS` overrides it. MOBO and MetaTAF keep PyTorch's default, because their hypervolume computations do benefit from threads (MOBO d=2: 3.9 s on 16 threads vs 7.3 s on one).
- **MetaTAF records its provenance** in a new `MetaRunState.json`, written atomically before the first trial (and on an aborted start, with `abort_reason`): library versions, how openbo is installed (pip's `direct_url.json`) plus SHA-256 hashes of the openbo modules in use (open-bo keeps version 0.1.0 across behaviour changes), the exact `MOTAFConfig`, the frame and its digest, the seed and init configuration, and the loaded, dropped and frame-rejected sources with their provenance stamps. The runtime now pins the `MOTAFConfig` fields it used to leave to openbo's defaults (`source_reference_mode="front"`, `source_reference_quantile=0.9`, `min_informative_pairs=1`, no meta-features — identical in every openbo that passes the TAF-R probe), so an upstream default change (e.g. to the newer `target_incumbent` reference) cannot silently alter a running study, and the weights log reads openbo's attributes directly, so a renamed attribute fails loudly instead of logging invented weights.
- `meta_train.py` publishes each artifact only after its self-check passes, and atomically: a failed or skipped source leaves nothing behind (the artifact used to be written before the check and stayed after a failure).
- One iteration axis for observation and metric logs: every row of `BestObjectivePerEvaluation.csv` / `HypervolumePerEvaluation.csv` now carries the same `Iteration` as its evaluation's row in `ObservationsPerEvaluation.csv`, and warm-start runs log their baseline at the iteration of the last current-context warm-start row. Under warm start, BoTorch had dropped the baseline row entirely since 1.7.1 (its metric list was one entry short) and numbered live rows 1, 2, … while its observations said k+1, k+2, …; MOBO logged the baseline as 0. Joining the files on `Iteration` paired metrics with the wrong evaluations.
- **DBO backend now runs dbo-torch 0.2.0** (vendored from [M-Colley/dbo-torch](https://github.com/M-Colley/dbo-torch) `main` @ `1a268cd`, adding `_base.py` and `PROVENANCE.md`). Changes that affect studies: each optimizer owns its random-number generator, so a run is reproducible from the inspector **Seed** alone and unaffected by anything else drawing from torch's global RNG; inputs are normalized against the fixed domain rather than the observed range, so fitted lengthscales keep their meaning between iterations; hyperparameters are fitted from three starting lengthscales, keeping the most likely fit; `PredictedCost`/`PredictedSd` are now predictions for the iteration at which the point is evaluated (previously the acquisition time, one iteration earlier by default); the incumbent and continuous-validation searches use BoTorch's `optimize_acqf` instead of hand-written loops. **Results for the same seed differ from 0.1.0 — do not mix versions within one study.**
- New per-run `DboRunState.json`: the optimizer's own record (dbo_torch/torch/botorch/gpytorch versions, full configuration, RNG state, every observation with its prediction), rewritten atomically after every evaluation, so each run is attributable to the library version that produced it and restorable with `DynamicBO.load()` for offline analysis. The dbo_torch version is also printed at startup.
- DBO validation scheduling is configured up front instead of being switched on after the sampling phase; dbo-torch never schedules a validation iteration while seed points are unspent, so the schedule is unchanged.

### Fixed
- **`DBO Initial Alpha = 1` silently produced a stationary run labelled as DBO.** Alpha can never be fitted away from exactly 1 (its gradient vanishes there): with dbo-torch 0.1.0 the fitted alpha stayed at 1.000000 on strongly drifting data where a 0.99 start fitted 0.982, and with 0.2.0 the same setting would crash at the first model fit, after the participant had completed the sampling phase. The inspector slider now stops at 0.999 and shows an error for 1, the launcher refuses to start, and the backend rejects it at init. Pin alpha = 1 with **DBO Stationary Baseline** instead.
- **DBO `BestObjectivePerEvaluation.csv` used a different iteration axis from every other backend**: one row `0` after sampling, then optimization steps `1..M`, while BoTorch/MOBO/MetaTAF have logged one row per evaluation on the global index (sampling included) since 1.7.1. DBO-vs-BoTorch curves were shifted by the number of sampling iterations; DBO now writes the same rows as `bo.py`.
- **Measurements could be recorded against a design the participant never saw.** Every questionnaire in the scene finds the manager and calls `OptimizationStart()` when it finishes, which sent the current objective values (the scale midpoint for objectives without values) even when no evaluation was in progress — e.g. a pre-study questionnaire finished after the optimizer was ready, or a second questionnaire finished after the next design had arrived. Python stored these as real observations of a design that was never shown. `OptimizationStart()` now only reports an evaluation in progress and otherwise logs a warning and does nothing.
- One non-numeric sub-measure (e.g. an unanswered optional item, submitted as NaN) replaced the whole objective with the scale midpoint, discarding the answered items; the objective is now the mean of its finite sub-measures (midpoint only when none is finite, as before).
- **Values on a decimal bound crashed the backend.** Bounds were sent as doubles widened from the inspector's floats (`0.7f` → `0.699999988079071`) while values were sent as floats (`0.7`), so a value clamped to, or rated at, such a bound failed the backends' bounds check and ended the session; warm-start rows on such a bound were rejected the same way, and MetaTAF frame fingerprints never matched a `frame.json` written with the typed bounds. Bounds are now sent as floats (`0.7`), identical to the values.
- **Non-ASCII keys or IDs (e.g. `Größe`, `Jürgen`) crashed the BoTorch/MOBO/MetaTAF backends at the end of the sampling phase**: Python wrote the CSV logs in the Windows code page but reads them back as UTF-8. The backend now runs in Python's UTF-8 mode (`PYTHONUTF8=1`), and its console output is decoded as UTF-8.
- Python dependency setup could hang forever ("Installing Python dependencies…") once pip wrote more to stderr than the pipe buffer holds, because stdout was read to the end before stderr; both are now drained concurrently.
- Backend tracebacks (stderr) are now written to `output.txt` as well, and the process-exit log no longer dereferences a process object that shutdown has already disposed.
- **CABOP: a fixed Seed did not reproduce a run.** The GP's hyperparameter restarts drew from numpy's global RNG; they now draw from the run's seed, and repeated runs with the same seed propose bit-identical designs.
- **CABOP: the "Sobol" initial design was i.i.d. uniform** — every point came from a freshly scrambled Sobol engine. The initial design is now one Sobol sequence per run (so initial designs differ from earlier versions for the same seed).
- **CABOP update rule `Both` entered every unsnapped observation twice**, so the GP treated noisy ratings as nearly exact; an intended design is now added only when snapping actually moved it.
- CABOP: a parameter whose lower and upper bounds are equal crashed the first GP fit after the sampling phase; it is now rejected at startup. A negative Seed (allowed by Unity) crashed the backend at startup; it is now wrapped into numpy's seed range. Group cost entries whose group name differed from the parameters' group only in letter case were silently replaced by default costs — Unity matches groups case-insensitively, and the backend now does too.
- **MetaTAF could still silently run as the no-transfer control.** `Meta Require Sources` checked the sources staged after frame validation, but openbo warns and *skips* artifacts it cannot use (an unreadable or half-synced trajectory, malformed hyperparameters, a front that never dominates the reference point). With every staged source skipped, the run continued as plain qLogNEHVI while the log still said "using N population model(s)" and `MetaSourcesUsed/` archived sources that were never used. The check now applies to what openbo actually loaded: dropped sources are reported with openbo's reason and removed from `MetaSourcesUsed/`, and the run aborts before the first trial when none is left.
- MetaTAF's `IsPareto` flagged every copy of a duplicated non-dominated objective vector, MOBO only the first; with tied (e.g. Likert) ratings MetaTAF reported more Pareto rows — and gave FinalDesignSelector a larger candidate pool — than BoTorch for identical data. Both now use the same semantics.
- `meta_train.py`: parameter values outside the frame's bounds that happened to lie in [0,1] were silently read as already normalized, so a run recorded under different bounds became a distorted source that the frame stamp then certified; such runs are now refused with the column and offending values. Restarts with a non-finite likelihood or hyperparameters are discarded (a NaN score on the first restart used to stay "best"), and `frame.json` bounds must be finite with low ≤ high.
- **Contextual optimization crashed whenever a configured context had no observations** — README 8.13's main use case (warm start from earlier participants, a new current participant) at startup, and any contextual run with two or more contexts and no warm start after the participant had finished the sampling phase. LCEMGP inherits `MultiTaskGP.eval()`, which in BoTorch 0.18.1 initialises unobserved tasks through an IndexKernel that LCEMGP does not have; the backends now skip that step, which is exact for LCEMGP (posteriors are unchanged when every context is observed). Note that with `Learned` embeddings a new context's embedding is untrained; use manual or image embeddings for transfer to new participants.
- MOBO crashed with exactly one current-context observation (a one-row warm start, or a new participant's first evaluation): NumPy 2 arrays also have `.device`, so NumPy input got a torch mask, and a one-element torch bool mask indexes as the integer 1.
- **IDs were rewritten in the observation log.** BoTorch, MOBO, MetaTAF and CABOP rewrite `ObservationsPerEvaluation.csv` after every evaluation through pandas, whose type inference turned `007`/`01`/`NA` into `7`/`1`/an empty cell in every row but the newest. FinalDesignSelector matches IDs as exact strings, so final-design selection found no candidates, and joins with the questionnaire logs broke. Logs are now read back as text; zero-padded warm-start `Context` keys load correctly too.
- A multi-byte UTF-8 character split across two socket reads was corrupted in every backend (`Größe` → `Gr��ße`, then a missing-key error); messages are now decoded incrementally.
- Parameter/objective keys that collide with fixed log columns (`Phase`, `Iteration`, `IsBest`, `IsPareto`, `UserID`, …) crashed BoTorch/MOBO/MetaTAF after the sampling phase and made the DBO/CABOP logs ambiguous; they are now rejected at startup.
- Warm-start parameter files: a raw value a hair outside its bounds (e.g. logged at 3 decimals) silently switched the whole column to the "already normalized" reading, remapping every value. Values within 0.05% of the range outside the bounds are now read as raw, and both the raw-vs-normalized choice (when both fit) and the normalized fallback are announced. CABOP now shares this detection with the other backends.
- Perfect-rating stop: the last sampling round's rating could start the "perfect twice in a row" streak although ratings from initial rounds were excluded (the check used the already-advanced iteration counter), and a perfect rating after a gap reset the streak instead of starting a new one, so stopping then took three perfect ratings in a row.

### Security
- **The optimizer backends listened on every network interface** (port 56001, no authentication), so any machine that could reach the lab PC could connect before Unity did and drive or read the study. All five backends now bind to `127.0.0.1` only — Unity always connects there.
- On Windows, `SO_REUSEADDR` let a second backend bind port 56001 while a leftover one (e.g. after a Unity crash) was still listening, so Unity's connection could land on the stale process. The backends now use `SO_EXCLUSIVEADDRUSE` on Windows (a second backend fails at startup with a message naming the leftover process; immediate restarts still work), keep `SO_REUSEADDR` on macOS/Linux where it only bridges `TIME_WAIT`, and stop listening as soon as Unity has connected.

### Licensing
- The CABOP optimizer is vendored from the authors' reference implementation ([aalto-ui/CABOP](https://github.com/aalto-ui/CABOP), MIT); its licence notice was missing and now ships as `cabop/LICENSE`, with the local changes listed in `cabop/__init__.py` and credited in README 8.7.

## [1.7.2] - 2026-08-20

### Changed
- **MetaTAF `TafR` weighting is now objective-wise pairwise ranking agreement** (openbo's 2026-08 TAF-R rework, formulation by Yi-Chi Liao): every observation pair is scored once per objective with ranking labels `r_ijm ∈ {+1, −1, 0}` (ties detected at 1e-12 tolerance), and a source's distance is its label mismatch count over the fixed denominator `M·C(n,2)`; a source asserting no strict order anywhere (flat surrogate) is zero-weighted outright. The former Pareto-dominance agreement discarded mutually non-dominated pairs — the common case near a Pareto front — and so starved the similarity estimate exactly where HITL studies operate; it stays selectable as the new `TafRPareto` inspector option (init token `taf_r_pareto`) for ablations.
- The MetaTAF backend now **refuses openbo installs predating that rework** at startup, printing the exact upgrade command (`pip install --force-reinstall --no-deps ...`; openbo kept version 0.1.0, so a plain `--upgrade` is a no-op). On a stale install the unchanged mode token `taf_r` would silently compute the old dominance similarity — variant drift across participants of one study. Documented in README 9 (troubleshooting), the student guide, and `requirements.txt`.

### Documentation
- Student guide: the new TAF-R formulation in the settings table and the paper-notation method summary, the `TafRPareto` ablation, the openbo upgrade path, and a note on tie semantics — with quantized ratings (e.g. Likert scales) target ties are common and shrink all sources' absolute weights by roughly the tie fraction (ordering between sources is preserved; mind this when tightening `Meta Rho`).

### Tests
- 2 new MetaTAF runtime tests (`taf_r_pareto` accepted and forwarded verbatim to `MOTAFConfig`; stale openbo rejected with the upgrade hint, distinct from the missing-package error; 198 total). On the openbo side the rework ships with regression tests for the reviewer's worked example (`d_s = 1/2`), tie semantics, the trade-off-curve edge case (dominance variant returns the null similarity result, ranking variant separates a copy from an inverted source), and a brute-force EHVI equivalence check (`exp(qLogEHVI)` vs `HV(front ∪ {μ(x)}) − HV(front)`, ~2e-7 relative error at M=2, ~7e-5 at M=3).

## [1.7.0] - 2026-07-29

### Added
- **DBO backend (Dynamic Bayesian Optimization)** for single-objective studies whose cost drifts during the session (participant adaptation, learning, fatigue). The GP covariance is multiplied by a temporal decay `alpha^|t-t'|` with the decay rate fitted by marginal likelihood, so the optimizer infers how fast the participant is changing; a `DBO Stationary Baseline` toggle pins `alpha = 1` for the matched plain-BO control condition, and optional validation iterations apply the model's best estimate on a schedule so optimizers can be compared without their exploration policies confounding the result. New `Backend -> DBO` inspector option with a dedicated settings section, `dbo.py`/`dbo_runtime.py` backend speaking the standard socket protocol and writing the standard CSVs, plus `DboDiagnosticsPerEvaluation.csv` with the fitted alpha per iteration. Implementation is the BSD-3-Clause [dbo-torch](https://github.com/M-Colley/dbo-torch) package (validated against the reference MATLAB DBO to ~1e-14), vendored under `BOData/BayesianOptimization/dbo_torch/`. Method: Kim & Sergi, Comput. Methods Biomech. Biomed. Eng. 2025 (doi 10.1080/10255842.2025.2595150) and IEEE RA-L 2026 (doi 10.1109/LRA.2026.3665072). See `docs/dbo-backend.md`; verify with `python tests/dbo_protocol_check.py` (manual, not part of unittest discovery).

## [1.6.1] - 2026-07-27

### Changed
- **MetaTAF fails fast when no population model survives validation** instead of silently running plain qLogNEHVI, which would turn a MetaTAF study condition into the no-transfer control. New `Meta Require Sources` inspector toggle (default ON, `metaRequireSources` init field); the startup error lists why each candidate source was rejected. Disable the toggle only for intentionally source-less runs.
- `meta_train.py` now **requires** `--source-type {human,llm-persona,synthetic}` and `--y-calibration {measured,generated}`: provenance is caller-declared instead of hardcoded `human`/`measured`, which mislabeled model-generated (e.g. LLM-persona) sources in every artifact and downstream `MetaSourcesUsed/` audit trail.
- `meta_train.py` fits each objective with 8 deterministic restarts and keeps the best fit, scored against the Standardize-transformed `gp.train_targets` (the quantity `fit_gpytorch_mll` maximizes) — guarding against degenerate "collapse to noise" fits on small noisy runs. Scoring restarts against raw targets would be systematically biased toward exactly those degenerate fits.

### Fixed
- Population-model artifacts now export the fitted GP's constant mean (`mean_constant`) and the openbo loader replays it, making the export->replay round trip bit-exact (previously the rebuilt model's mean defaulted to 0 in standardized space and deviated in data-sparse regions). Needs the matching openbo update; older artifacts still load unchanged (constant 0). Regenerate artifacts to benefit.
- A source whose Pareto front never strictly dominates the reference point `[-1]^M` (an objective stuck at its worst bound) is refused by `meta_train.py` up front, and the openbo optimizer warn-skips such a source at construction instead of aborting the participant session.

### Tests
- 2 new MetaTAF runtime tests (fail-fast on zero and on all-rejected sources; 195 total), plus 2 new tests in openbo (mean-constant replay, warn-skip at optimizer construction; 40 total there).

## [1.6.0] - 2026-07-25

### Meta-BO backend (MetaTAF, TAF-EHVI)
- New `MetaTAF` optimizer backend (`meta_mobo.py` / `meta_mobo_runtime.py`): multi-objective Meta-Bayesian optimization that blends the current user's BoTorch `qLogNEHVI` model with hypervolume-improvement terms from **population models** built from prior participants' runs (Transfer Acquisition Function lifted to Pareto/hypervolume optimization, following Wistuba et al. 2018 and Liao et al. CHI 2024, including their population-weight decay `γ(t)`). Population models that disagree with the current user's observed Pareto rankings are automatically down-weighted; with zero valid sources the acquisition degenerates exactly to plain multi-objective BO.
- The multi-objective optimizers (`mobo_botorch`, `mobo_taf`, `acquisition/taf_mo_ehvi`) live in the [openbo](https://github.com/M-Colley/openbo) package (MIT, © Yi-Chi Liao; fork with correctness fixes and the new multi-objective code) — an optional dependency installed only for this backend; the runtime fails fast with the install command when missing. Not added to the auto-installed `requirements.txt` (needs git; documented in README 8.14 and `docs/meta-taf-student-guide.md`).
- New offline tool `meta_train.py` converts completed runs' `ObservationsPerEvaluation.csv` into population-model artifacts (per-objective GP fits, normalized into the canonical frame, self-checked by reloading through the runtime's own loader).
- Every artifact carries the study **frame** (parameter/objective names, bounds, minimize flags); the runtime skips sources whose frame differs from the live study, field by field — transferring across mismatched bounds or a flipped minimize flag would silently import a rescaled or inverted response surface.
- New outputs per run: `MetaWeightsPerEvaluation.csv` (target weight, decay factor, and per-source weights per iteration) and `MetaSourcesUsed/` (audit copy of the exact population models the run used).
- Unity integration: `OptimizerBackend.MetaTAF`, inspector section (source dir, weight mode TafR/TafM, rho, target weight, warmup, decay d1/d2), init-message fields, and fail-fast validation (multi-objective only; Warm Start and Contextual Optimization are rejected with actionable errors).
- Hardening: the backend isolates PyTorch's JIT extension cache per process (`TORCH_EXTENSIONS_DIR`), preventing an infinite startup hang caused by stale lock files after a killed run.

### Shared frame modules
- Added `bo_normalize.py`: the canonical frame (parameters in `[0,1]^d`, objectives in `[-1,1]` maximization with the minimize-flag sign flip) extracted into one shared, dependency-light module. `bo.py` and `mobo.py` now delegate to it instead of each carrying their own copy; behaviour is unchanged and the objective format is an explicit argument rather than a module global.
- Added `meta_fingerprint.py`: canonical frame fingerprint + field-by-field difference reporting (used by `meta_train.py` and the MetaTAF runtime).

### Fixed
- The contextual-optimization guards in `PythonStarter`, `SocketNetwork`, and the inspector now check for "backend is not BoTorch" instead of "backend is CABOP", so newly added backends cannot silently bypass the LCE-M restriction.

### Tests
- 48 new tests (193 total): shared-frame parity against `mobo.py`'s live transform, frame-compatibility detection, and a full protocol/CSV test of the MetaTAF runtime against a stubbed openbo (CI-safe: numpy+pandas only). The contextual/embedding suites are unchanged and pass.

### Documentation
- README 8.14 (Meta-BO overview + troubleshooting rows) and `docs/meta-taf-student-guide.md` (student walkthrough: population-model workflow, settings, logged outputs, study-design guidance, citations).

## [1.5.0] - 2026-07-16

### Contextual Optimization (LCE-M GP)
- Added contextual multi-task optimization built on BoTorch's `LCEMGP` (Feng et al., NeurIPS 2020) for both the single-objective (`bo.py`) and multi-objective (`mobo.py`) BoTorch backends.
- Context embeddings are definable: learned from data, supplied manually per context (any encoder, e.g. ViT-G/14 vectors), or computed from context images via open_clip (default `ViT-bigG-14`, the open_clip release of ViT-G/14) with content-hashed caching and optional L2 normalization.
- Warm-start parameter CSVs accept a `Context` column to transfer observations from other contexts (users, devices, environments); new observations are tagged with the current context.
- Run metrics (`coverage`, `IsBest`/`IsPareto`, hypervolume/best-objective traces) and the logged `Iteration` index are computed over current-context observations only; `ObservationsPerEvaluation.csv` gains a `Context` column.
- New `BoForUnityManager` inspector section with live validation and fail-fast startup checks; contextual mode is BoTorch-only (CABOP rejects it with a clear error).
- Worked around a BoTorch `LCEMGP` task-kernel dimensionality issue when `context_emb_feature` is provided.

### CABOP Fixes
- Fixed a critical parameter-ordering bug: with multiple CABOP groups whose parameters interleave in declaration order, parameter values were silently assigned to the wrong parameter names (in Unity payloads, observation logs, and warm-start data). Vectors now always follow parameter declaration order.
- Fixed a spurious `AssertionError` when the acquisition optimizer landed exactly on a parameter bound (floating-point overshoot); proposals are now clamped to bounds.
- `IsBest`/`IsPareto` marker flags are now derived from full-precision scalarized values instead of the rounded CSV values, and no longer re-scan the whole CSV every iteration.
- Zero-configured costs and degenerate GP predictions no longer produce division-by-zero in the acquisition function.
- The CABOP runtime now tolerates malformed/unrelated protocol messages the same way as the BoTorch backends.

- Fixed a pandas dtype issue when writing `IsBest` flags during `bo.py` sampling runs.
- Context image paths configured on Windows now also resolve on macOS/Linux.
- `MainThreadDispatcher` no longer holds its queue lock while running actions, and one failing action can no longer abort the rest of the frame's queue.
